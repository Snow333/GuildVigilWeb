B · QUEST BOARD — THE HIERARCHY YOU ASKED FOR

Target weighting: title loudest, then level, then time, then reward at level's weight, with difficulty as a named category. Level / time / reward are equal-sized blocks read left to right in priority order; difficulty sits directly under the title as the headline judgement, because it is the one field that should stop you accepting. Everything that is neither a decision nor a deadline drops to one muted footer line.

E · DECISIONS I NEED FROM YOU BEFORE ANY CODE

1 · DIFFICULTY BANDS — WORDING AND THRESHOLDS

Bands derive from challenge − partyLevel, reusing the autopilot's existing accept rule (it declines anything above partyLevel + 1), so the board says what the guild would say. Four bands map onto the frozen status set, always label-paired.

OPTION A — PLAINEasy · Fair · Hard · Too hard
Unambiguous, zero flavour, translates cleanly.
OPTION B — THE GUILD'S JUDGEMENT (shown above)Routine · Measured · Dangerous · Beyond us
Reads as a marshal's opinion of the job, which is what the desk fiction is.

Thresholds either way: ≤ −2 routine · −1…0 measured · +1 dangerous · ≥ +2 beyond us.

2 · PROFILE LABELS — REGISTER

Option A ("Search everything") is functional and unmistakable. Option B ("Sweep it clean") sounds like an order given to people. B fits the desk fiction better; A is easier to be certain about. Ids stay frozen either way.

3 · REGIONAL PRESSURE ON THE BOARD

I removed it from the notice, because it describes the region rather than the job and it was outshouting the difficulty. It still appears on the town hub watch report and the chart. Alternative: keep it as a muted word in the footer line (THE ASHMARK · QUIET) so you can still see a region heating up while choosing work. Say the word and I will add it back that way.

4 · SCOPE — THIS IS A UX BRIEF, NOT A DRIVE-BY

Four surfaces, one new sim query (the difficulty band), one presentation label map, no schema change, no new content. By your own process this wants an implementation brief before code. I would rather write the short version of that brief off your answers above than start editing components — the last thing this repo needs is grammar erosion introduced by a readability pass.
